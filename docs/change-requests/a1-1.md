# Change Request A1-1
- Betroffener Abschnitt im MASTER_PLAN: 3.5 (System-/UI-API), 3.3 (data/ext), 3.4 (State)
- Problem (konkret, mit Beispiel):
  1. A8 braucht in `ships/board` die Selektoren von A5 (`skills/hasRequirements`). Ein System hat laut 3.5 nur `ctx.{state,data,rng,now,emit}` und kann fremde Selektoren nicht lesen.
  2. Views müssen nach Actions und Ticks aktualisiert werden; `game.on('core/ticked')` deckt Actions nicht ab.
  3. `data/ext/*.json` lässt sich im Browser nicht per Glob laden.
  4. Es gibt keine definierte Einstiegsfunktion der Shell, die `boot.js` aufrufen kann.
  5. Zufall muss über Save/Load deterministisch bleiben.
- Vorschlag (Feld/Action/Event exakt benannt), alles additiv und ohne neue Actions/Events:
  1. `ctx.select(type, args)`, `ctx.tick` (= `state.tick`), `ctx.offline` (true beim Nachholen), `ctx.log(text, kind)`; Selektoren erhalten `select` als 4. Parameter.
  2. `game.subscribe(fn) → unsubscribe`, aufgerufen nach jedem Tick-Block und jeder erfolgreichen Action. Dazu `game.hasAction(type)`, `game.hasSelector(type)` für `view.enabled()`, `game.t(key, params)` für i18n.
  3. `data/ext/index.json` (Dateiliste); `tools/serve.mjs` erzeugt sie dynamisch, Pages-Deployment braucht sie nicht, weil der Lead ext vor Release faltet.
  4. Shell-Vertrag: `js/ui/shell/index.js` exportiert `mount(root: HTMLElement, game, { views, warnings })`. `boot.js` ruft es auf, wenn die Datei existiert, sonst Notbehelf-Panel.
  5. `state.rngState` (uint32) als Teil des State; `ctx.rng` basiert darauf.
- Auswirkung auf andere Agenten: A3 implementiert `mount(...)` und nutzt `game.subscribe`. A4–A9 dürfen `ctx.select` nutzen (statt direkter Imports fremder Systeme). A2 ändert nichts.
- Dringlichkeit: blockiert mich nicht (bereits so implementiert) / für A3 und A8 wünschenswert vor Welle 2

## Entscheidung Lead (10.11.2026)
Angenommen, eingearbeitet als MASTER_PLAN 3.7 (Contract 1.1). `ext/index.json` bleibt dynamisch (nur serve.mjs); `data/ext/.gitkeep` ergänzt.
